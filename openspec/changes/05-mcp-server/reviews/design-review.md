## Design review: 05-mcp-server

Intent: provide a stateless, multiuser MCP endpoint for activity and report tools, forwarding each caller's token to the REST API.

### Findings (most severe first)

- [must-fix][architecture] `apps/mcp/src/services/activity-tools.service.ts:9`, `apps/mcp/src/services/activity-tools.service.ts:13`, `apps/mcp/src/services/report-tools.service.ts:8`, `apps/mcp/src/repositories/taskory-api.client.ts:31` — Services construct REST paths, query strings and HTTP methods through a generic `request`, so API transport details spread through both services. This violates the repository boundary in `docs/agent-rules.md` and makes endpoint changes service changes. Give the existing API client intent-named activity/report methods and move URL and method construction there; services should pass domain arguments. Both services are called by their corresponding tool registrations.
- [should-fix][bad practices] `apps/mcp/src/repositories/taskory-api.client.ts:17`, `apps/mcp/src/repositories/taskory-api.client.ts:20`, `apps/mcp/src/http/server.ts:43`, `apps/mcp/src/tools/tool-result.ts:9` — A successful `/auth/me` is cached for 30 seconds, contrary to the no-cache non-goal in `openspec/changes/05-mcp-server/design.md` and `proposal.md`. If revoked during that window, discovery and other MCP-only operations can still succeed; a subsequent API-backed tool forwards the revoked token, but its API 401 becomes a tool error instead of the required HTTP 401 challenge. The API still enforces authorization for its data; the cache does not grant access to API data by itself. The window is undocumented and is not acceptable against the current explicit no-cache and 401 requirements. Remove the cache and validate each request; also design and test how a 401 occurring after validation can trigger the required challenge, including revocation races. If the team wants a revocation window instead, first change the spec and document the precise trade-off; documentation alone does not fix tool-call 401 handling.
- [should-fix][bad practices] `apps/mcp/src/http/server.ts:33` — Browser preflight `OPTIONS /mcp` is sent without the actual bearer token and gets 401; no CORS response headers are emitted for actual responses either. Browser-based cross-origin MCP clients therefore cannot connect or read the challenge. Handle preflight before bearer validation and define an appropriate origin policy, allowed methods/headers, and exposed `WWW-Authenticate` and MCP headers for actual responses. This is a browser interoperability gap; the spec does not explicitly require CORS.
- [should-fix][bad practices] `apps/mcp/src/tools/list-activities.tool.ts:9`, `apps/mcp/src/tools/list-activities.tool.ts:15` — Only the first API page is reachable: the API defaults to 50 and allows at most 200, but the tool exposes no `page` even when the returned `total` is larger. The response is passed through, so total/page/limit are retained at runtime, but an agent cannot retrieve remaining matching records and may mistake a partial list for a complete answer. Add optional `page`, document default and maximum limit and explain using `total` and `page` to continue; add a multi-page test.
- [should-fix][bad practices] `apps/mcp/src/services/activity-tools.service.ts:8`, `apps/mcp/src/tools/log-activity.tool.ts:11` — “Today” uses the server's timezone, as the design currently specifies, so an activity can be recorded on the wrong calendar day for a user in another timezone near midnight. Smallest fix: instruct the agent in the date description to supply the user's local date whenever known, and disclose the server-local fallback; for a guaranteed user-local date, require or obtain a timezone/date, which needs a spec decision. Test a date boundary with controlled time and timezone.
- [should-fix][bad practices] `apps/mcp/package.json:14`, `apps/mcp/src/tools/log-activity.tool.ts:13` — The runtime-only `npm audit --omit=dev` reports one high advisory, GHSA-mrhx-c7xc-m3w5, for installed Zod 3.25.76: oversized constrained collections can exhaust memory. The tools validate arrays with `.max(20)`, and the SDK's 4 MiB body cap bounds input bytes but does not establish immunity to the advisory. Audit identifies this as a direct production dependency, not merely a dev dependency; it reports Zod 4.6.7 as a major-version fix. Upgrade to a compatible fixed version after checking SDK compatibility, or document and verify an effective upstream mitigation. The audit output does not establish exploitability or demonstrate an actual denial of service.
- [should-fix][bad practices] `apps/mcp/src/repositories/taskory-api.client.ts:31`, `apps/mcp/src/tools/tool-result.ts:9` — A fetch timeout/network failure becomes generic `INTERNAL_ERROR`; an API 5xx is emitted using whatever code and message the API supplies, like a 4xx. The caller cannot reliably distinguish transient connectivity or server failure from internal faults and client-correctable errors. Map timeout/network and upstream 5xx to stable, safe, retryable availability errors, preserve actionable 4xx codes, and test each path. The 15-second abort signal is already present.
- [should-fix][bad practices] `apps/mcp/src/tools/validation.ts:3`, `apps/mcp/src/tools/log-activity.tool.ts:13`, `apps/mcp/src/tools/update-activity.tool.ts:14` — Business validation is independently duplicated in MCP and API and already diverges: MCP accepts year `0000` while `apps/api/src/common/dates/is-calendar-date.ts:2` rejects it, and Zod URL validation allows schemes that `apps/api/src/activities/dto/activity-field-validators.ts:20` rejects. MCP also omits API length constraints on descriptions, tags and project. Keep schema shape and useful descriptions at the boundary, make the API authoritative for business rules, or share a contract; add contract tests for the cases retained in both places.
- [should-fix][tests] `apps/mcp/test/requirements.test.ts:19`, `apps/mcp/test/requirements.test.ts:81`, `apps/mcp/test/validation-and-errors.test.ts:11`, `apps/mcp/test/http-lifecycle.test.ts:5` — The named zero-configuration scenario only inspects a header, not OAuth discovery/authorization; the date test compares against a second live clock and can cross midnight; validation converts any thrown exception into success; lifecycle coverage only makes sequential successful calls and does not verify close on disconnect or errors. Add deterministic boundary tests that assert the actual failure contract, revocation after cache warming, malformed JSON-RPC, 413/header limits, CORS and close behavior; keep the real OAuth/API scenario explicitly pending until it can be run. `apps/mcp/test/support/mcp-system.ts:43` and `fake-taskory-api.ts:64` bind ephemeral local ports, so these tests were not run under the no-server instruction. No test sleeps or cross-test shared mutable state were found in the reviewed suite.
- [should-fix][tests] `apps/mcp/test/services.test.ts:5`, `apps/mcp/test/http.test.ts:5`, `apps/mcp/test/reports.test.ts:8` — Many test groups and cases do not use the exact requirement/scenario names required by `docs/agent-rules.md`; test files also live in a central `test/` folder rather than next to the unit. Existing `requirements.test.ts` provides some traceability, but several of its named cases do not establish the full scenario. Organize and name tests as the project rule specifies, and use accurate names for narrower checks.
- [should-fix][formatting] `apps/mcp/src/http/server.ts:30`, `apps/mcp/src/tools/update-activity.tool.ts:20`, `apps/mcp/src/repositories/token-validation-cache.ts:13` — Chained statements and compressed one-line branches conflict with the explicit readable one-statement-per-line rule in `docs/agent-rules.md`. Expand these and similar cases; no MCP formatter check script or formatter configuration was found in the scoped package.

### Done well

- `apps/mcp/src/http/server.ts:53` creates a fresh MCP server and stateless transport per request, attaches an idempotent response-close cleanup, and catches connect/dispatch errors. No lifecycle leak is established from inspection; disconnect during the preceding async token check and rejected close promises still need tests.
- `apps/mcp/src/repositories/taskory-api.client.ts:21` caches SHA-256 digests, and `apps/mcp/src/repositories/token-validation-cache.ts:22` bounds entries to 1,000 with fixed 30-second expiry and LRU eviction. No source logging of tokens was found. `apps/mcp/src/config.ts:30` normalizes an origin ending in `/`, and `apps/mcp/src/http/www-authenticate.ts:2` produces the exact required challenge for the normalized configuration. Tool descriptions distinguish activity searches, report generation and asynchronous report retrieval, and describe parameters.

### Verification and limits

- The taskory repository is not indexed by the available codebase-memory service; impact analysis used source reads and `rg` instead. Review scope is the untracked `apps/mcp` tree against HEAD and the named OpenSpec documents; other working-tree changes are context only. No commit hygiene assessment applies.
- Installed SDK 1.32.2 defaults to a 4 MiB streamed body limit and returns 413 for oversized bodies; malformed JSON receives HTTP 400 / JSON-RPC -32700, and invalid JSON-RPC is rejected. Node 24 reports a 16 KiB default maximum header size in this environment; the app does not pin either default. Bearer tokens are separately limited to 512 characters. These observations are based on installed dependency source and runtime configuration, not end-to-end tests.
- `npm audit --omit=dev --json` completed with one high production advisory (nonzero audit exit). Tests, coverage, real OAuth/API integration and formatter checks were not run: integration tests start servers and no formatter check was configured. The README references a missing `.env.example` (`apps/mcp/README.md:7`); remove the reference or provide the file.
